# 14 — 垃圾回收器（引用计数 + 增量循环检测）

> **概括**：本篇精读 `asCGarbageCollector`（as_gc.h / as_gc.cpp，不到 1000 行）。AngelScript 的对象生命周期主体是**引用计数**，GC 只做一件事：找出并打断引用计数永远回不到零的**循环引用**。核心算法是"试减引用计数"式的循环检测（与 Bacon & Rajan 的 trial deletion 思想同源），并被精心拆成可以每次只走一小步的**状态机**，以便游戏在每帧预算内增量执行。
>
> **难度**：★★★☆☆（代码量小、注释充分；难点在状态机各阶段的正确性论证与并发假设）
>
> **前置**：第 05 篇（类型系统，`asOBJ_GC` / `asSTypeBehaviour`）、第 12 篇（脚本对象 `asCScriptObject` 的引用计数与内存布局）。

涉及文件：
- `sdk/angelscript/source/as_gc.h` / `as_gc.cpp`（回收器本体）
- `sdk/angelscript/source/as_scriptobject.cpp`（脚本类对象的 GC 协议实现）

## 1. 模块定位：引用计数补漏者，而非全权管理者

与 JS/Lua 的 tracing GC 本质不同：那些语言里**所有**对象的存活性都由 GC 从根集合可达性判定，析构时机不确定；AngelScript 里对象由引用计数管理（as_gc.h:35 的文件头注释一句话点题："The garbage collector is used to resolve cyclic references"）——计数到零立刻析构，**确定性释放**。GC 只登记"可能参与循环"的对象，周期性地检查它们是否已经变成了只被圈内同伴引用的孤岛。

由此推出几条设计约束：

- GC 对每个登记对象**额外持有一个引用**（AddScriptObjectToGC 里先 addref，as_gc.cpp:86），所以在 GC 列表中的对象 refCount 最小是 1。"refCount == 1"即"只剩 GC 自己在引用"= 纯垃圾，可直接释放。
- GC 不能 stop-the-world 地扫描全堆——它根本不知道全堆，只知道自己列表里的对象；对象内部藏了哪些引用，必须靠对象自己通过 behaviour 回调**主动交代**（第 5 节）。
- 检测期间应用还在跑，对象可能被脚本触碰。算法用一个 gcFlag（"从上次 SetFlag 以来没被 AddRef/Release 过"）来发现干扰并重来，而不是加锁冻结世界。

## 2. 数据结构总览（as_gc.h:53-147）

- `gcNewObjects` / `gcOldObjects`（as_gc.h:114-115）：**两代列表**。新对象进 new 列表；在 new 列表里被扫过约 3 轮仍不死的对象移入 old 列表（第 4 节）。循环检测只针对 old 列表跑。
- `gcMap`（as_gc.h:122）：一轮检测期间的工作集，key 是对象指针，value 是 `{gc 视角的外部引用计数, 类型}`（asSIntTypePair，as_gc.h:75）。
- `liveObjects`（as_gc.h:118）：检测中已判活、待传播"存活性"的对象栈。
- 两个状态机枚举：`egcDestroyState`（as_gc.h:78-83，3 个状态）与 `egcDetectState`（as_gc.h:85-101，**14 个状态**：clearCounters / buildMap / countReferences / detectGarbage(loop1/loop2) / verifyUnmarked / breakCircles 各自的 init+loop）。所有循环变量（destroyNewIdx、detectIdx、gcMapCursor…）都是成员而非局部变量——这正是"可以在任意一步 return、下次接着跑"的物质基础。
- 两把临界区锁（as_gc.h:145-146）：`gcCritical` 保护列表的增删（AddScriptObjectToGC 可能从多个线程同时进来），`gcCollecting` 保证同一时刻只有一个线程在跑回收逻辑（GarbageCollect 入口用 TRYENTER，抢不到就直接返回 1，as_gc.cpp:172-179）。`isProcessing` 再挡掉同线程重入（例如析构回调里又触发 GC）。

## 3. 算法核心：IdentifyGarbageWithCyclicRefs 状态机（as_gc.cpp:626-936）

思想一句话：**如果把"圈内对象互相持有的引用"全部从 refCount 里减掉之后某对象计数归零，那它的所有引用都来自圈内，是循环垃圾**。实现上不真减对象的 refCount，而是在 gcMap 里给每个对象记一个影子计数，用枚举引用来递减——这正是 Bacon-Rajan"试删除（trial deletion）"的变体。每个 case 处理一个对象就 `return 1`（把控制权还给应用），下次调用从断点继续。

状态流转全景（正常路径自上而下；`←` 为回退边）：

```text
clearCounters_init → clearCounters_loop      清空上轮残留的 gcMap
      ↓
buildMap_init → buildMap_loop                收录 refCount>1 的 old 对象，记影子计数
      ↓
countReferences_init → countReferences_loop  枚举引用，圈内引用抵消影子计数
      ↓
detectGarbage_init → detectGarbage_loop1     影子计数>0 或 flag 被清 ⇒ 判活
              → detectGarbage_loop2          活性沿引用边传播，活者移出 map
      ↓
verifyUnmarked_init → verifyUnmarked_loop    幸存者 flag 被清? ── 是 ──→ 回 detectGarbage_init
      ↓ 否
breakCircles_init → breakCircles_loop        map 余下皆循环垃圾：析构 + ReleaseAllRefs
      → breakCircles_haveGarbage → 回 clearCounters_init（return 0/1 结束本轮）
```

逐阶段对照代码：

1. **clearCounters**（as_gc.cpp:639-658）：清理上一轮残留——把仍留在 gcMap 里的对象逐个 release（抵消 buildMap 时加的引用）并归还节点。注：状态名叫 clearCounters 是历史原因，实际工作是清空 map。
2. **buildMap**（as_gc.cpp:665-709）：遍历 `gcOldObjects`，凡 refCount > 1 的对象（refCount==1 的是纯垃圾，留给 DestroyGarbage 处理，不掺和进来）插入 gcMap，影子计数初值 = `refCount - 1`（减 1 是刨掉 GC 自己那份，as_gc.cpp:689），随后对对象 addref（防止检测中途被释放，694）并调用 `gcSetFlag`（698）打标记。
3. **countReferences**（as_gc.cpp:718-748）：对 map 里每个 gcFlag 仍立着的对象调用 `gcEnumReferences` 行为（739）。对象对自己持有的每个引用回调 `GCEnumCallback`；回调发现该引用指向 map 内对象时，**把被指对象的影子计数减 1**（as_gc.cpp:974-983）。这一阶段结束后：影子计数 > 0 的对象存在 GC 看不见的外部引用，必活；**计数 == 0 的对象所有引用都来自 map 内部，疑似循环垃圾**——这就是任务描述里"refCount 与 gcCount 相等者疑似只被圈内引用"的代码形态（gcCount 从 refCount-1 起步、被圈内引用逐一抵消到 0）。gcFlag 已被清掉的对象说明期间被应用 AddRef/Release 过，直接视为活。
4. **detectGarbage**（两个子循环）：
   - loop1（as_gc.cpp:758-788）：把"确定活"的对象（`!gcFlag || it.i > 0`，777）收集进 `liveObjects`；
   - loop2（as_gc.cpp:790-821）：从 liveObjects 逐个弹出，移出 gcMap（= 判活），release 抵消 buildMap 的加引用（809），再 `gcEnumReferences` 一次（812）——此时 GCEnumCallback 的语义切换为"把被引用者也放进 liveObjects"（as_gc.cpp:984-993）。即**活性沿引用边传播**：活对象引用的对象也活。传播完后，仍留在 map 里的就是彼此循环引用的死岛。
5. **verifyUnmarked**（as_gc.cpp:828-857）：最后一道保险——重查每个幸存者的 gcFlag；若有对象在检测期间被应用触碰（flag 被 AddRef/Release 清掉，842），回退到 `detectGarbage_init` 重跑传播。全部干净才敢下结论。
6. **breakCircles**（as_gc.cpp:859-930）：map 里剩下的全是循环垃圾。先给调试用的 `circularRefDetectCallbackFunc` 一次性通知（868-881）；然后逐个：`numDetected++`，脚本对象先补调析构函数（903，必须赶在句柄置空前，否则析构里访问成员句柄全是 null），再调 `gcReleaseAllReferences`（905）强制放掉它持有的一切引用。**GC 自己不 delete 任何对象**——打破循环后各对象的 refCount 自然跌到 1（只剩 GC 那份），由下一轮 DestroyGarbage 以正常 release 路径收尸。

影子计数的抵消发生在 `GCEnumCallback`——对象的 EnumReferences 对每个持有的引用回调它：

```cpp
// as_gc.cpp:974-983（countReferences_loop 阶段的分支）
if( detectState == countReferences_loop )
{
    asSMapNode<void*, asSIntTypePair> *cursor = 0;
    if( gcMap.MoveTo(&cursor, reference) )
        gcMap.GetValue(cursor).i--;   // 圈内引用：影子计数减 1
}
```

**销毁阶段** DestroyNewGarbage / DestroyOldGarbage（as_gc.cpp:361-471 / 514-624）逻辑对称：线扫列表，`gcGetRefCount() == 1` 的对象立即 release；期间还要提防析构函数"复活"对象（refCount 又升上去了就把 GC 的引用补回来，as_gc.cpp:406-429）。每释放一个对象可能让它引用的对象也跌到 1，所以置 `destroyGarbage_haveMore` 标志、扫完再来一圈（449-453）。DestroyOldGarbage 还多一个兜底：类型的 GC 行为函数已被引擎释放时（循环引用把类型实体拖到比实例还晚死），只能报错并放弃析构（as_gc.cpp:548-563）。

## 4. 增量性与两代列表

**为什么能一步一步跑**：所有阶段的每一次"处理一个对象"后都 `return 1`；游戏主循环每帧调 `GarbageCollect(asGC_ONE_STEP, n)` 就只消耗 n 小步。增量分支的全部逻辑：

```cpp
// as_gc.cpp:232-244（GarbageCollect 的非 FULL_CYCLE 分支）
while( iterations-- > 0 )
{
    if( doDestroy )
    {
        DestroyNewGarbage();
        DestroyOldGarbage();
    }
    if( doDetect && gcOldObjects.GetLength() > 0 )
        IdentifyGarbageWithCyclicRefs();
}
```

`asGC_FULL_CYCLE`（as_gc.cpp:186-229）则先 `MoveAllObjectsToOldList`（192）保证全量覆盖，然后 while 到状态机吐 0 为止，外层再循环直到 old 列表长度不再变化（205-224）——因为打破一个环释放的对象可能又让别的对象变成垃圾。

**两代列表的真实作用**（不是分代 tracing GC 那种"晋升"语义）：
- 新对象大概率短命——刚创建的临时数组、闭包，往往几帧内 refCount 就到 1。`DestroyNewGarbage` 高频线扫 new 列表就能廉价收掉它们，**完全不必跑昂贵的循环检测**。
- 一个对象在 new 列表里熬过约 3 轮完整扫描（用创建序号 seqNbr 与 `seqAtSweepStart[0..2]` 这个三格滑动窗口比较判定，as_gc.cpp:378-380 + 436-442，代码注释自己都在问"3 是不是个好值"）就移入 old 列表。
- 循环检测（IdentifyGarbageWithCyclicRefs）**只扫 old 列表**（as_gc.cpp:678）：活得久的对象才值得怀疑是循环垃圾；同时这让检测的工作集在一轮内相对固定，新创建的对象天然"视为活"（as_gc.cpp:729-730 注释），不会破坏正在进行的检测。

## 5. 对象的 GC 协议：五件套 behaviour

注册校验在 as_scriptengine.cpp:2544-2591：GC 行为**只允许注册给带 `asOBJ_GC` 标志的类型**（2548-2552），且签名严格（GETREFCOUNT 必须 `int f()`、ENUMREFS/RELEASEREFS 必须 `void f(int&in)` 即接收引擎指针，2554-2579）。反过来，`PrepareEngine` 会检查每个 asOBJ_GC 引用类型五件套是否注册齐全（as_scriptengine.cpp:3396-3405），缺一个就报配置错误。

| behaviour | 职责 | GC 在哪些阶段调用 |
|---|---|---|
| `asBEHAVE_GETREFCOUNT` | 返回当前引用计数 | buildMap、Destroy 阶段判 ==1 |
| `asBEHAVE_SETGCFLAG` | 置位 gcFlag | buildMap |
| `asBEHAVE_GETGCFLAG` | 读 gcFlag（**AddRef/Release 必须清掉它**） | countReferences、detectGarbage、verifyUnmarked |
| `asBEHAVE_ENUMREFS` | 对持有的每个引用调 `engine->GCEnumCallback(ptr)` | countReferences（减影子计数）、detectGarbage_loop2（传播活性） |
| `asBEHAVE_RELEASEREFS` | 放掉持有的全部引用并置空 | breakCircles |

注册长这样（scriptarray.cpp:366-370，去掉断言后）：

```cpp
engine->RegisterObjectBehaviour("array<T>", asBEHAVE_GETREFCOUNT, "int f()",
                                asMETHOD(CScriptArray, GetRefCount), asCALL_THISCALL);
engine->RegisterObjectBehaviour("array<T>", asBEHAVE_SETGCFLAG,   "void f()",
                                asMETHOD(CScriptArray, SetFlag),   asCALL_THISCALL);
engine->RegisterObjectBehaviour("array<T>", asBEHAVE_GETGCFLAG,   "bool f()",
                                asMETHOD(CScriptArray, GetFlag),   asCALL_THISCALL);
engine->RegisterObjectBehaviour("array<T>", asBEHAVE_ENUMREFS,    "void f(int&in)",
                                asMETHOD(CScriptArray, EnumReferences), asCALL_THISCALL);
engine->RegisterObjectBehaviour("array<T>", asBEHAVE_RELEASEREFS, "void f(int&in)",
                                asMETHOD(CScriptArray, ReleaseAllHandles), asCALL_THISCALL);
```

实现要点：
- `GetRefCount` / `SetFlag` / `GetFlag` 就是三个一行函数（scriptarray.cpp:1968-1983）；
- **关键约定**在 AddRef/Release 里，这是 gcFlag "被触碰即失效"语义的全部实现：

  ```cpp
  // scriptarray.cpp:1947-1952
  void CScriptArray::AddRef() const
  {
      gcFlag = false;          // 清掉 GC 打的标记
      asAtomicInc(refCount);
  }
  ```

- `EnumReferences`（scriptarray.cpp:1907-1938）：若元素是引用类型，逐个 `engine->GCEnumCallback(d[n])`；若元素是需要 GC 的值类型，用 `ForwardGCEnumReferences` 转发进去；
- `ReleaseAllHandles`（scriptarray.cpp:1941-1945）：整个函数就一句 `Resize(0)`——清空缓冲区自然释放全部元素引用，是"打破循环"的最省事写法；
- 构造函数末尾按需登记：`if( objType->GetFlags() & asOBJ_GC ) NotifyGarbageCollectorOfNewObject(this, objType)`（scriptarray.cpp:493-495）。注意 array 是模板类型，模板回调可以对具体实例说"元素类型不可能形成循环"（如 `array<int>`），引擎便摘掉该实例的 asOBJ_GC 位（as_scriptengine.cpp:3796-3798），实例就完全不进 GC。

脚本类对象的实现（`asCScriptObject`）是同一协议的引擎内置版：行为注册在 as_scriptobject.cpp:302-306；`EnumReferences` 遍历类的属性表，对句柄/引用成员逐个回调，对含 GC 的值类型成员递归转发（as_scriptobject.cpp:816-843）；`ReleaseAllHandles` 释放并置空所有句柄与 funcdef 成员（845-887）；AddRef/Release 同样先清 gcFlag（608-616）。

## 6. 触发时机

- **对象创建时登记**：脚本类实例在构造函数里 `if( objType->flags & asOBJ_GC ) engine->gc.AddScriptObjectToGC(...)`（as_scriptobject.cpp:344-346）；宿主类型通过公开接口 `NotifyGarbageCollectorOfNewObject`（as_scriptengine.cpp:5094-5097）。哪些脚本类带 asOBJ_GC 由编译器保守判定：编译期先全部假定 GC（as_builder.cpp:2529），编译完成后分析成员类型能否构成环、继承自 GC 类型则必 GC，再决定保留或摘除标志（as_builder.cpp:4090-4093、4232-4235）。委托/funcdef 对象也进 GC（as_scriptfunction.cpp:384）。
- **登记时顺手做增量回收**：`AddScriptObjectToGC` 本身就是自动 GC 的第一触发点——只要 `ep.autoGarbageCollect`（默认开，as_scriptengine.cpp:686；由 `asEP_AUTO_GARBAGE_COLLECT` 开关，374-375）为真，每次新对象进来就跑一步检测 + 最多 10 步销毁（as_gc.cpp:93-124），"以进养出"维持列表规模。
- **脚本执行结束后**：`asCContext::Execute` 返回前，按本次执行新增的对象数跑等量的增量步——创建越猛回收越勤：

  ```cpp
  // as_context.cpp:1572-1585
  if( m_engine->ep.autoGarbageCollect )
  {
      asUINT gcPosObjects = 0;
      m_engine->gc.GetStatistics(&gcPosObjects, 0, 0, 0, 0);
      if( gcPosObjects > gcPreObjects )
          m_engine->GarbageCollect(asGC_ONE_STEP | asGC_DESTROY_GARBAGE | asGC_DETECT_GARBAGE,
                                   gcPosObjects - gcPreObjects);
      else if( gcPosObjects > 0 )
          m_engine->GarbageCollect(asGC_ONE_STEP | asGC_DESTROY_GARBAGE | asGC_DETECT_GARBAGE, 1);
  }
  ```
- **应用手动调用**：`engine->GarbageCollect()` 默认 `asGC_FULL_CYCLE`（angelscript.h:788）；四个标志位见 angelscript.h:322-328。全量周期完成后引擎还会顺手删除被 GC 对象拖住的已弃模块（as_scriptengine.cpp:5110-5115）。引擎关停时残留对象由 `ReportAndReleaseUndestroyedObjects` 逐个报错并强制放掉 GC 引用（as_gc.cpp:473-512）。

## 7. 关键代码走读

1. **as_gc.cpp:78-134 `AddScriptObjectToGC`**：先 addref（86）确立"GC 持有一份引用"的全局不变量；中段的自动增量回收用 TRYENTER + isProcessing 双保险避免跨线程/同线程重入；尾部在 gcCritical 里分配递增序号 seqNbr 并入 new 列表（128-131）。返回序号可供调试定位泄漏对象。
2. **as_gc.cpp:397-445 DestroyNewGarbage 的一步**：`gcGetRefCount()==1` → release；`asOBJ_SCRIPT_OBJECT` 走特殊路径处理析构复活（407-411）；否则若 `seqNbr < seqAtSweepStart[0]`（三轮前就存在）移入 old 列表（436-441）。注意每个分支后都 `return 1`——"让应用喘口气"的注释（444）出现了十多次，是全文件的节奏基调。
3. **as_gc.cpp:683-699 buildMap 收录一个对象**：`refCount-1` 作影子计数初值、addref、SetFlag，三个动作定义了后续所有阶段依赖的不变量。
4. **as_gc.cpp:969-994 `GCEnumCallback`**：同一个回调按 `detectState` 呈现两种语义——countReferences_loop 时减影子计数，detectGarbage_loop2 时把引用目标推入 liveObjects。对象侧的 EnumReferences 实现完全不需要知道现在是哪个阶段。
5. **as_gc.cpp:892-912 breakCircles 处理一个死对象**：脚本对象先 `CallDestructor()`（903）再 `gcReleaseAllReferences`（905）的顺序是硬约束——反过来析构函数看到的成员句柄全是 null。
6. **as_scriptobject.cpp:816-843 `asCScriptObject::EnumReferences`**：数据驱动的枚举——遍历 `objType->properties`，按属性的 DataType 判断是句柄、引用类型还是需转发的 GC 值类型。第 12 篇讲的对象布局（属性 byteOffset）在这里直接派上用场。

## 8. 如果你要自己实现

1. **第一版：纯引用计数**。AddRef/Release/析构，文档里写明"不许循环引用，循环导致泄漏"。这已经覆盖 95% 场景，且析构确定性是脚本嵌入宿主时的巨大优点（资源句柄、RAII）。
2. **第二版：泄漏检测器**。维护一个"可疑对象"登记表 + 让对象实现 EnumReferences，程序退出时报告哪些对象没死、引用计数还剩多少——即 `ReportAndReleaseUndestroyedObjects` 的功能。先能"看见"循环，再谈"解决"。
3. **第三版：全量试删除**。停下世界，对登记表跑一遍"影子计数 = refCount − 内部引用数，归零者为循环垃圾"，然后 ReleaseAllRefs 打破循环。正确性容易论证，但停顿不可控。
4. **第四版：增量化**。把第三版的每个循环改写成"成员变量保存游标 + 每步 return"的状态机；引入 gcFlag（AddRef/Release 清、GC 置）作为"检测期间被触碰"的脏标记，加 verifyUnmarked 兜底重跑；最后加 new/old 双列表把廉价的"扫计数==1"与昂贵的循环检测分频。到这一步你就重新发明了 as_gc.cpp。

## 9. 动手实验

`samples/asrun/bin/script.as:62-66` 有现成的循环引用：

```angelscript
class Link { Link @next; }        // script.as:115-118
{
  Link @link = Link();
  @link.next = link;              // 自引用环，离开作用域后 refCount 永不为 0
}
```

实验：在宿主（可改 samples/asrun/source/main.cpp，它在 main.cpp:466 已有全量 GC 调用）中，脚本执行前后与 GC 各阶段之间插入：

```cpp
asUINT cur, det, destr, newObj;
engine->GetGCStatistics(&cur, &destr, &det, &newObj, 0);
printf("size=%u destroyed=%u detected=%u new=%u\n", cur, destr, det, newObj);
```

建议观察序列：(a) 先关掉自动 GC（`engine->SetEngineProperty(asEP_AUTO_GARBAGE_COLLECT, 0)`）让垃圾积攒；(b) 跑完脚本后打印——`currentSize` 非零，`totalDetected` 为 0；(c) 只跑 `GarbageCollect(asGC_DETECT_GARBAGE | asGC_FULL_CYCLE)`——`totalDetected` 增加（Link 环被识破）但对象仍在；(d) 再跑 `asGC_DESTROY_GARBAGE`——`totalDestroyed` 增加、`currentSize` 落零。两阶段的分工由此可见。也可以用 `SetCircularRefDetectedCallback` 拿到每个循环垃圾对象的类型与指针。

## 10. 扩展阅读
